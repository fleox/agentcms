# S3-compatible bucket (AWS, OVHcloud, Scaleway, Cloudflare R2, MinIO)

The admin writes files straight into the bucket with signed requests from the browser. The bucket needs:

1. a key pair allowed to read / write / delete / list objects;
2. **CORS** allowing the admin's origin(s);
3. public read access for visitors, and ideally **static website hosting** (index.html for folder URLs).

If the `aws` CLI is installed, offer to do 2 and 3 for the user, and import 1 from an aws profile.

## Values for the plan

| Setting | AWS | OVHcloud | Notes |
|---|---|---|---|
| `endpoint` | empty | `https://s3.<region>.io.cloud.ovh.net` | Scaleway `https://s3.<region>.scw.cloud`, R2 `https://<account>.r2.cloudflarestorage.com` |
| `region` | e.g. `eu-west-3` | e.g. `eu-west-par`, `gra`, `sbg` | R2: `auto` |
| `bucket` | bucket name | bucket name | |
| `publicRead` | `false` (use a bucket policy) | **`true`** (OVH has no bucket policies) | sends `x-amz-acl: public-read` |
| `siteUrl` | website / CloudFront URL | see below | With a `prefix`, include it: `http://<bucket>.s3-website.<region>.io.cloud.ovh.net/<prefix>` |
| `prefix` | optional | optional | Puts the whole site (pages, admin, media, database) in a sub-folder of the bucket, e.g. `blog`. Use it to share a bucket between sites; never reuse another site's prefix. |
| `forcePathStyle` | `false` | **`true`** | How the admin and the CLI address the bucket API. MinIO also needs `true`. |

## Key pair

- From an existing aws CLI profile: `npx -y @agent-cms/agentcms@0.3.0 credentials set s3:<name> --from-aws-profile <profile> --json`.
- AWS: IAM user with `s3:GetObject`, `s3:PutObject`, `s3:PutObjectAcl`, `s3:DeleteObject`, `s3:ListBucket` on this bucket only.
- OVHcloud: Public Cloud -> Object Storage -> **S3 users** -> create a user with access to the bucket, then show its credentials (access key + secret).
- Otherwise the user runs `! npx -y @agent-cms/agentcms@0.3.0 credentials set s3:<name>` and types both values.

## CORS (aws CLI)

Origins = where the admin runs: the bucket's HTTPS endpoint (hosted admin) and `http://localhost:4173` (`agentcms serve`). Add the custom domain if any.

```bash
cat > /tmp/agentcms-cors.json <<'JSON'
{ "CORSRules": [ {
  "AllowedOrigins": ["https://<bucket>.s3.<region>.io.cloud.ovh.net", "http://localhost:4173"],
  "AllowedMethods": ["GET", "PUT", "DELETE", "HEAD", "POST"],
  "AllowedHeaders": ["*"],
  "ExposeHeaders": ["ETag"],
  "MaxAgeSeconds": 3600 } ] }
JSON
aws --endpoint-url <endpoint> s3api put-bucket-cors --bucket <bucket> --cors-configuration file:///tmp/agentcms-cors.json
```

(Omit `--endpoint-url` on AWS.)

## Static website hosting

```bash
aws --endpoint-url <endpoint> s3api put-bucket-website --bucket <bucket> \
  --website-configuration '{"IndexDocument":{"Suffix":"index.html"},"ErrorDocument":{"Key":"404.html"}}'
```

AWS also needs "Block public access" off for the bucket and a public-read bucket policy on `arn:aws:s3:::<bucket>/*`.

## Site URL and HTTPS (important)

The browser admin signs requests with WebCrypto, which only exists on **HTTPS** pages (or localhost). Website endpoints are often HTTP-only:

- OVHcloud website endpoint `http://<bucket>.s3-website.<region>.io.cloud.ovh.net` serves folders (index.html) but is HTTP. The HTTPS endpoint `https://<bucket>.s3.<region>.io.cloud.ovh.net` works for the admin at `/admin/index.html` (it doesn't serve folder indexes).
- Best for production: a custom domain with HTTPS in front (CDN such as Cloudflare or CloudFront) -> use it as `siteUrl`.
- For a test, `siteUrl` = the website endpoint is fine. The admin must still be opened over HTTPS: `install`, `site list` and `doctor` give that address as `adminUrl` (e.g. `https://<bucket>.s3.<region>.io.cloud.ovh.net/<prefix>/admin/index.html`). Make sure that origin is in the CORS rules.

## Sites in a sub-folder (`prefix`)

- A bucket has **one** error page, which is shown for every missing URL, under every prefix. A sub-folder site therefore shows the bucket root's 404 page (often another site's). Tell the user, or give the site its own bucket.
- Search engines only read `robots.txt` at the domain root. On a sub-folder site, submit the sitemap (`<site URL>/sitemaps/sitemap-index.xml`) in Google Search Console instead.

## Plan fragment

```json
"hosting": { "type": "s3", "settings": { "endpoint": "https://s3.eu-west-par.io.cloud.ovh.net", "region": "eu-west-par", "bucket": "<bucket>", "forcePathStyle": true, "publicRead": true, "prefix": "<optional sub-folder>", "siteUrl": "<site URL, with the prefix>" }, "credential": "s3:<name>" }
```

SQLite data on a public bucket is encrypted by default (the file is still downloadable, but unreadable without the passphrase). For a database that is never served at all, keep it in a second, **private** bucket (no public-read, no website hosting; same CORS rules) as the data location:

```json
"data": {
  "backend": "sqlite-file",
  "path": "site.sqlite",
  "location": { "type": "s3", "settings": { "endpoint": "<endpoint>", "region": "<region>", "bucket": "<private-bucket>" }, "credential": "s3:<name>" }
}
```

Create it like the site bucket but skip the website / public-read steps: `aws --endpoint-url <endpoint> s3api create-bucket --bucket <private-bucket>` (plus `put-bucket-cors` with the admin origins).

With Markdown content and an S3 hosting, the browser needs the bucket keys once to publish: admin -> Settings -> Publish target.
